## 六、实测后判定「不改」的项（避免以后重复评估）

| 项 | 结论 |
|---|---|
| 等待循环每 20ms 调 100 次 `pump`（怀疑空转烧 CPU） | **否决**：等待 2 秒的 CPU 时间 150ms → 140ms（噪声内）；等待实际走 `scheduler.await()` |
| 每条 UPDATE 多一次 `map.put`（页锁 + 可能分裂） | **否决**：2 万次更新的耗时 95–112ms vs 95–110ms（稳态无差异） |
| 二级索引游标 `rowSnapshots` 无上界（担心大表扫描吃满堆） | **否决**：无法隔离收益（`-Xmx120m` 时插入阶段先 OOM），且加上限会牺牲去重正确性 |
| 页面写「提交重试」整页重序列化（怀疑 2 倍行拷贝） | **否决**：插桩实测重试率 **0.35%（单线程）/ 0.18%（4 线程）** |
| SLT 门禁 `rowsort` 只排实际结果不排期望值 | **改错已回退**（（整理时已删除的 rowsort 回退））：语料期望值本就按约定排序，把期望值当扁平列表再排会打散多列行对齐，门禁失败数从 14 暴涨到 13,656 |
| `ROLLBACK TO SAVEPOINT` 是否也有语句缓存陈旧问题 | **实测无问题**（保存点回滚后本会话立刻能读到正确结果），**不做过度防御** |
| `RowType` 读页面时统一补 LOB handler；`SHUTDOWN`/GC 的 `getSessionCount()` 判据 | **未采纳**：构造不出「不改就失败」的用例 / SHUTDOWN 的执行会话本身就还在，无法证明必要 |

## 七、SLT 语料的方言差异清单（判断「真 bug 还是方言」用）

门禁的 oracle 是 SQLite，以下差异是**设计使然**，不是缺陷：

| 类别 | Lealone（= H2 / 标准 SQL） | SQLite |
|---|---|---|
| `TEXT` 类型 | 映射成 CLOB → 不能建唯一索引 | 动态类型，可索引 |
| 除零 | 报错 `Division by zero` | 返回 NULL |
| 整数溢出 | 报错 `Numeric value out of range` | 64 位自动提升 |
| `COALESCE(int, AVG(...))` 参与除法 | 静态类型 → REAL 除法 | 动态类型 → 整数除法 |
| `AVG(int)` 类型 | 返回 DOUBLE（H2 兼容），类型会传播到外层表达式 | 返回 REAL，但动态类型使外层保持整数语义 |

台账里 12 条已登记的失败全部属于上表；门禁按**失败签名**比较，所以「修好一条、又坏掉一条」也能被发现。

## 八、这一批里最有代表性的一次排查（值得复用）

「事务内查询之后 `ROLLBACK` 在本会话里看不到撤销结果」这个问题花了 **4 轮**、换了 **5 次判断**才定位，
结论是给后来人最有价值的部分：

| 轮次 | 当时以为的原因 | 推翻它的证据 |
|---|---|---|
| 1 | 级联删除的 undo 记录丢了 | 不带外键的普通删除也丢；两个缺陷其实是同一个 |
| 2 | 失败的 DDL 破坏了会话状态 | 无任何失败语句时也复现 |
| 3 | MVCC / undo log 记账错 | 插桩显示 rollback 与 undo 都**正确执行**了 |
| 4 | 客户端 packet 被吞 | 服务端收到了 ROLLBACK，`AOTransaction.rollback()` 也执行了 |
| 5 | **会话的语句缓存复用了回滚前的游标状态** | **第二个连接回滚后立刻看到 2 行，只有本会话读到旧结果**；同一条 `SELECT` 被 `[QC] reuse` |

方法论收获（已写进台账）：
1. **多连接对照**是区分「引擎真错」与「会话内视图陈旧」的最快手段；
2. TCP 用例的服务端是**独立进程**，验证前必须核对监听 9210 的 PID 与构建，否则会误测旧版本（我们踩过三次）；
3. 给超时加**线程栈转储**（`DiagnosticTimeout`）后，原本"超时 300 秒"的偶发挂死一次就定位到了 `latch.await()` 无超时。
